## What was built

### Stage one — make the model really use the tool

`StrandsOllamaInterpreter._stages` builds one fresh `Agent` with the single
read-only, workspace-bound `read_inventory` tool, `callback_handler=None`,
`load_tools_from_directory=False`, `retry_strategy=None`, and invokes it with
`limits=Limits(turns=6)` and the caller's `cancel_signal` — and **no**
`structured_output_model`. Its only job is genuine tool selection and execution.

The prose it writes is never parsed, never shown and never becomes evidence.
Calling the Python tool directly, or manufacturing metrics, would not qualify as
tool execution, so neither is done. `_require_real_inventory` refuses the run
unless a workspace read actually completed: it rejects an exhausted send budget,
a cancelled run, any limit stop reason, an over-budget tool attempt, SDK metrics
that disagree with what the tool itself recorded, and a success count outside
`1..2`. One corrective continuation is still available, and only for a normally
completed run that executed zero tools.

### Stage two — schema extraction from the source alone

`_extract` calls the owned model's own `structured_output` once, with a message
list built here from the intake text only, and a dedicated extraction system
prompt. No agent conversation, tool result or inventory count is passed in, so
none of it can become a default or be mistaken for evidence. The stream is
closed in a `finally`, and a run that ends without an `output` event, or with
something that is not the schema type, is refused rather than turned into a draft
of nulls.

This is where the schema actually constrains decoding:
`OwnedOllamaModel.structured_output` sets
`request["format"] = output_model.model_json_schema()`, which is Ollama's own
schema parameter. That is a different mechanism from the R2 path — see the
corrections section.

### Shared bounds

Both stages and the continuation share one `OwnedOllamaModel`, one
`RequestBudget(6)`, one `_ToolBudget(2)` and one 110 s `asyncio.timeout`. The
provider is entered manually and closed in the `finally` on every path. `_close`
records the real outcome: a failed close sets `cleanup=close_failed` and the
error is re-raised only when no other exception is already in flight, so a
cleanup failure can never be silently swallowed *or* mask the real error.

### Credential inheritance

`ollama/_client.py` `BaseClient.__init__` reads `OLLAMA_API_KEY` and sets
`headers['authorization'] = f'Bearer {api_key}'` whenever the slot is empty.
`trust_env=False` does not disable this — it governs httpx's proxy and netrc
handling, not this code. The owned provider therefore supplies
`{"Authorization": LOCAL_AUTHORIZATION_MARKER}` through the documented `headers`
client argument, occupying the slot so an inherited key has nowhere to go. The
marker authenticates nothing, the destination is loopback, and the local server
ignores it.

No environment variable is read, written or deleted by the implementation.

### Shutdown ownership

New `InferenceRegistry` and `DrainReport` in `interfaces/http/inference_slot.py`,
owned by a FastAPI `lifespan`. The route checks `registry.closing` and raises
`AssistantUnavailableError` (503) before acquiring the slot; the check and the
`register` call happen in one event-loop step, so no drain can begin between
them. `register` never raises — a run somehow registered after a drain began is
signalled immediately rather than left unattended.

`drain(timeout)` sets `closing`, signals every registered cancel event, and
`asyncio.wait`s the tasks for a bounded 10 s. It returns
`requested / ended / abandoned` and the lifespan logs exactly that. A run that
ignores its signal is logged as still running. **No claim is made that a local
model was made to stop computing** — cancellation here is cooperative and both
the docstring and the log say so.

### Accounting

`_emit` writes one terminal line per interpretation from the `finally` path, so
failures and cancellations are covered as well as successes: correlation id,
stage, reason, charged sends, tool attempts and successes, recovery use, elapsed
ms, cleanup result. It carries no intake text, candidate values, evidence spans,
prompts, model reasoning or headers.

`scripts/assistant_smoke.py` now writes a `start` record **before** the request
leaves, flushed and fsynced, then an `end` record after. An attempt that never
returns is therefore still charged. `_consumed` counts pre-ledger BS-003 probes
(`PRE_LEDGER_ATTEMPTS = 5`), legacy phase-less lines, and distinct `start` lines,
and reports how many started without ending. A `--ceiling` guard (default 19)
refuses to send anything that would take the total past it.

## Live proof: three probes, stopped at the first failure

Implementation frozen before the first probe; nothing in `src/` changed between
the offline PASS and the three calls.

| # | Case | Status | Time | Sends | Tools | Recovery | Cleanup |
|---|---|---|---|---|---|---|---|
| 9 | explicit fields | 200 | 6.41 s | 3 | 1 | no | closed |
| 10 | relative date | 200 | 1.27 s | 3 | 1 | no | closed |
| 11 | ambiguous kinds | 200 | 1.47 s | 3 | 1 | no | closed |

`sends=3` on all three is stage one, its tool continuation, then the single
extraction request. Snapshot byte-identical before and after all three.

**Probe 9 failed its required case.** It grounded `borrower_label`,
`pickup_location` and `due_at` — the last for the first time on a required case —
but returned `equipment_kind: null` for a message reading "Meena R needs a
wheelchair...". The case exists to show stated fields surviving grounding, so it
failed at its purpose, and the pass stopped there with three probes unspent.

Reason codes locate the fault: `absent_candidate` means the model returned null,
so grounding rejected nothing. Probe 10 shows the same on "walker". Probe 11,
naming two kinds, logged `ambiguous_kinds` — a real proposal refused by the rule
— so the ambiguity rule works and probe 11's null is a genuine pass.

**Diagnosis, not acted on.** The `equipment_kind` schema description reads "Null
if the message names no kind, or more than one." It states only the null case;
every other field's description leads with what to extract. A one-line reword is
the likely fix. I did not make it: the implementation was frozen, and rewording
then re-probing until a case passes is the loop this process exists to prevent.

## Corrections to my own BS-003-R2 claims

Appended dated to `test-evidence/probe-ledger.md` and `docs/workers/BS-003-R2.md`.
Nothing earlier was rewritten.

1. **Withdrawn — retry causality.** R2 claimed `retry_strategy=None` was the main
   cause of its 502s and made that the headline question for Codex. Contradicted
   by the installed source: `event_loop/_retry.py` defines
   `ModelRetryStrategy.is_retryable` as
   `isinstance(exception, ModelThrottledException)` and nothing else, and
   `StructuredOutputException` is raised on a separate path in `event_loop.py`
   where the loop forces the structured-output tool and gives up. The setting
   could not have affected those failures in either direction.
2. **Corrected — constrained decoding.** "Ollama's constrained decoder" did not
   describe the R2 path, where the schema went to
   `Agent.invoke_async(structured_output_model=...)`: that exposes a
   structured-output *tool* and asks the model to call it, which constrains
   nothing at the decoder. The claim is accurate only of the R3 stage-two path.
   The observed R2 improvement was real; the mechanism given for it was wrong,
   and with two attempts per variant it is not separable from run-to-run variance.
3. **Marked unknown — the "—" counters.** R2 ledger rows 2, 4, 5 and 8 show "—"
   for model requests and tool calls. Those runs failed before the accounting
   line was emitted, so the counts were never observed. They are unknown, not
   zero: each sent at least one request. Treating "—" as 0 understates real model
   traffic. R3's terminal telemetry line closes this hole.
