### The two findings that carry the report

**1. The 30-second cadence is infeasible, and Vercel cannot schedule it at all.**
Hobby cron is "once per day" with ±59 minute precision, and a more frequent
expression **fails at deployment** - so the scheduler must be external whatever
else is decided. GitHub Actions' floor is 5 minutes. The binding constraint is
then Neon: 100 CU-hours/month at a 0.25 CU minimum is 400 awake hours against 720
in a month, a 55% duty ceiling, while scale-to-zero at 5 minutes idle means a
tick every *T* minutes holds the compute awake about 5/*T* of the time. A 30-second
tick keeps it awake permanently: ~180 CU-hours, 80% over. **The smallest cadence
I can honestly propose is 15 minutes (~60 CU-hours).** Ten minutes is
arithmetically inside but leaves ~10 CU-hours for all human traffic. I did not
authorize any change; the decision is stated as Codex's.

**2. Groq's structured-output restriction fits the existing two-stage design.**
Groq documents that "Streaming and tool use are not currently supported with
Structured Outputs", and strict mode wants all fields required with
`additionalProperties: false`. M2A already runs stage one with real tools and
deliberately no `structured_output_model`, and stage two with one schema request
and no tools - the two halves land on opposite sides of that restriction, and
`_Extraction`'s eight fields are already all required and nullable. This
compatibility is accidental rather than designed, and I said so. It is the reason
the migration is adapters rather than a rewrite.

### Source-grounded design points

- `sqlite3` is imported in exactly **one** file, so the Postgres adapter is a
  sibling of `sqlite_store.py`, not a refactor of the application.
- `requires-python = ">=3.11"` is compatible with Vercel's default Python 3.12
  (3.11 is not offered), so no source change is needed for the interpreter.
- `OpenAIModel` accepts `client_args` (so `base_url` reaches Groq) and its
  `structured_output` calls `client.beta.chat.completions.parse(...,
  response_format=output_model)` - the strict json_schema path. It builds a
  client per request in `_get_client`, so the owned-client problem
  `OwnedOllamaModel` solves largely disappears; the request budget does not and
  must be re-implemented on a subclass.
- `OwnedOllamaModel` is a native Ollama client and is **not** a portable API
  client. It stays for local development. Nothing hosted is relabelled as Ollama.
- Neon's pooler is PgBouncer in transaction mode: no SQL-level `PREPARE`, session
  variables or `LISTEN`/`NOTIFY`. Migrations therefore use the direct endpoint
  and `pg_advisory_xact_lock`, never a session-level advisory lock.
- The report states the required contract amendments explicitly rather than
  silently freezing them: `agent_mode` must stop saying `strands_ollama`,
  provenance must carry the real provider and model id, and the new internal tick
  route is not part of the public contract.
- `InferenceSlot` is process-local; the report says plainly that a process-local
  lock cannot enforce an account-wide free quota across Vercel instances, and
  moves admission into the database.

## KNOWN_ISSUES

- **The Active CPU estimate is the weakest number in the report.** Vercel Hobby
  includes 4 CPU-hours; my 1-2 s per cold tick is an estimate, not a measurement,
  and it drives whether ~2,880 monthly ticks fit. The separate minimal tick
  function exists to protect that margin. Marked as an estimate in the report.
- **Token cost per interpretation is also an estimate.** The 5,518-character
  stage-two prompt is a real measurement from BS-007; converting it to ~1,400
  tokens is not.
- **Groq free-tier permanence is unverified.** The rate-limit page presents free
  alongside paid tiers but does not say the free tier is permanent, so continuity
  through 9 October cannot be asserted.
- **Groq's acceptance of the OpenAI SDK `.parse()` helper specifically is
  unverified.** Groq documents strict json_schema and shows Pydantic examples but
  does not name that method, and Strands' `structured_output` uses exactly it.
  This is the compatibility risk most likely to need a live check first.
- Neon's page does not state whether a suspended compute accrues usage; the
  documentation only implies it does not. Treated conservatively.
- GitHub Actions disables scheduled workflows after 60 days of repository
  inactivity. The judging window is ~24 days from submission, so this is not a
  live risk, but it is a real cliff if the project idles afterwards.
