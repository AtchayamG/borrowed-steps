## 3. IMPLEMENTATION & RESOLUTION OF BS-002-R3 REQUIREMENTS

### Requirement 1: Route general mutation refusals inside the active modal/action
- **Implementation**:
  - `apps/web/src/api/client.ts`: Added `isStructuredError: boolean` flag to `ApiClientError` to track whether a non-2xx response contained a valid structured API error JSON body (`error.code`, `error.message`).
  - `apps/web/src/App.tsx`:
    - Added `dialogError: string | null` state and `isLoanActionOpen: boolean` state.
    - Derived `isModalOpen = Boolean(allocatingRequest || inspectingEquipment || isLoanActionOpen)`.
    - In `executeMutation`: on terminal mutation refusal (HTTP 400, 403, 404, 422, or structured 500), formats `Submission error (${err.code}): ${err.message}` and assigns it to both `setServerError` and `setDialogError`.
    - Page-level `{serverError && ...}` is conditionally rendered only when `!isModalOpen`, preventing errors from rendering behind the backdrop.
    - Passed `error={dialogError}` and `onClearError` callback to `AllocationModal`, `InspectionModal`, and `LoanList`.
    - Automatically clears `dialogError` and `serverError` whenever modals open, close, or switch active actions.
  - `apps/web/src/components/AllocationModal.tsx`:
    - Accepts `error?: string | null` and `onClearError?: () => void`.
    - Renders `(error || serverError)` inside `.modal-content` with `role="alert"`.
    - Clears previous error messages when the selected equipment changes or the volunteer approval checkbox toggles.
    - Preserves current user inputs (selected equipment, volunteer approval) upon refusal; does not trigger post-success close.
  - `apps/web/src/components/InspectionModal.tsx`:
    - Accepts `error?: string | null` and `onClearError?: () => void`.
    - Renders `(error || serverError)` inside `.modal-content` with `role="alert"`.
    - Clears previous error messages when outcome determination changes or approval checkbox toggles.
    - Preserves selected determination and approval state upon refusal; modal remains open.
  - `apps/web/src/components/LoanList.tsx`:
    - Accepts `error?: string | null`, `onClearError?: () => void`, and `onActionChange?: (isOpen: boolean) => void`.
    - Renders `(actionError || serverError)` inside `.modal-content` with `role="alert"`.
    - Clears errors when opening, closing, or toggling approval.
    - Notifies `App` of open/closed action state via `onActionChange`.
- **Verification**: `src/test/CodexR2Regression.test.tsx` [Tests 1, 2, 3] PASS; `apps/web/scripts/browser-verify.js` [Test 5] PASS.

### Requirement 2: Distinguish structured server errors from connection failures
- **Implementation**:
  - `apps/web/src/api/client.ts`: Sets `isStructuredError = true` whenever `response.json()` yields an `ApiErrorResponse` with `error.code` and `error.message`. Non-JSON responses (e.g. empty 500 on proxy `ECONNREFUSED` or HTML 502/503) default to `isStructuredError = false`.
  - `apps/web/src/App.tsx`:
    - Updated `SnapshotErrorState` to include `code?: string` and `isConnectionFailure: boolean`.
    - In `fetchSnapshot` and `handleStartWorkspace`:
      - If `err.isStructuredError` is `true`: classifies as server error (`isConnectionFailure = false`), sets `code: err.code, message: err.message`.
      - If `err.status === 0 || err.code === "CONNECTION_ERROR" || (err.status === 500 && !err.isStructuredError)`: classifies as connection failure (`isConnectionFailure = true`).
    - In JSX error rendering:
      - If `snapshotError.isConnectionFailure`: renders `OfflineBanner` ("Connection Error: ...") with `Retry Connection` button.
      - If `!snapshotError.isConnectionFailure`: renders Server Error banner (`role="alert"`, `<strong>Server Error (${snapshotError.code}):</strong> ${snapshotError.message}`) with `Retry Snapshot` button.
- **Verification**: `src/test/CodexR2Regression.test.tsx` [Test 4] PASS.
