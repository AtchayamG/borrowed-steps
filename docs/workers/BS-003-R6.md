## Criterion 1 — smoke validation aligned with the real diagnostic

`_check_case` required `diagnostic["stage"] == "complete"`. The adapter assigns
`stage` exactly three times — `inventory`, `inventory_recovery`, `extraction` —
and never rewrites it afterwards, so a successful run's terminal stage is
`extraction` and `complete` has never existed. Every genuinely successful live
run would have been reported as a failed proof.

Fixed by introducing `TERMINAL_SUCCESS_STAGE = "extraction"` and checking
against it. No public schema and no prompt changed; these names are the
adapter's internal diagnostic vocabulary.

The reason this was invisible is that the offline tests hand-wrote
`"stage": "complete"` in seven places. Those now reference
`assistant_smoke.TERMINAL_SUCCESS_STAGE`, so a test double can no longer
disagree with the source of truth.

**The faithful boundary test** (`test_smoke_boundary.py`): the real
`StrandsOllamaInterpreter` runs inside the real application, served by uvicorn on
a real loopback port, and the real smoke `Client` reads the real
`X-Assistant-Diagnostic` header off the wire and feeds it to the real
`_check_case`, which must return no failures. The only fake is the provider
transport, an in-process `ollama.AsyncClient` stand-in; no model runs and no
socket to a model is opened. A second test reads the adapter's source and
asserts the stage vocabulary is exactly those three values.

I verified these are real regressions rather than tests that merely pass: with
`TERMINAL_SUCCESS_STAGE` set back to `"complete"`, both fail (exit 1); with the
correction, both pass.

## Criterion 2 — one owned close per model

`_close` created a close task, cancelled it on timeout, and could then start a
second while the first was still running. The saved
`reviews/BS-003-R5-close-repro.py` printed `peak concurrent closes=2`.

The fix is small and has one idea: **the close operation is owned**.
`_closing: dict[model, Task]` holds it; `_close_operation` returns the running
one and starts a new one only when the previous is `done()`, cancelled or not;
`_await_close` waits a bounded time and, on expiry, requests cancellation but
keeps owning the task; `_close_settled` retrieves a late result so a failure
after the wait is reported instead of surfacing as an unretrieved task
exception. `_close` and `resolve_cleanup` both go through it, so shutdown and the
per-run path can never race each other. The registry does the same for the one
cleanup supervisor task it creates.

What is bounded is the *waiting*, not the work. A close that resists
cancellation keeps running; the code says so, and no test or comment claims a
resistant close can be forced to stop.

Re-running the saved reproduction against this worktree now prints
`peak concurrent closes=1`, with the resistant close still active and still
owned.

## Criterion 3 — a failed pre-case snapshot stops before anything is sent

`main` fetched the pre-case snapshot, wrote the attempt-start charge, sent the
interpretation, and only later graded the snapshot statuses. A case whose
baseline had failed therefore spent allowance and reached the model although it
could never have shown that interpretation wrote nothing.

The pre-case snapshot is now a prerequisite, checked immediately after it is
fetched and before both the ledger charge and the request. `_snapshot_problem`
rejects a non-200 and a 200 whose body lacks the collections the comparison
relies on. Earlier charged attempts are untouched, and the evidence file records
`stopped_at_case`.

One honesty detail: when a run stops before any case completes,
`business_snapshot_unchanged` is now `null` rather than `true`. With nothing
observed, "unchanged" would be vacuous truth reported as evidence.

## CORRECTION - 2026-09-08, appended during BS-003-R7 (append-only; nothing above edited)

Criterion 2 above is overstated, and the accompanying claim in
`docs/REVIEW_QUEUE.md` that "ownership survives timeout, parent cancellation and
shutdown" was **false for parent cancellation**. The correct statement:

Ownership survived cancellation only in `_closing`, the private dict. Every
consumer that acted on it - the refusal at the top of `interpret`, the
`cleanup_unresolved` property the HTTP slot reads, and the `resolve_cleanup`
loop shutdown drains - read a *second* record, `_unresolved`, which was appended
to only in `_close`'s failure tail. A cancellation arriving mid-close left
`_close` before that tail, so `_unresolved` stayed empty while `_closing` held a
live close task on a client that was still open. Everything that mattered
reported nothing outstanding, and the slot was handed to the next request, which
opened a second client.

The nine tests in `tests/test_close_ownership.py` did not catch this because
they asserted against `_closing` - the record that was correct - rather than
against what any consumer read or what the service actually did next. They were
true statements about a private field, not about the behaviour they were taken
to prove. Both HTTP-path tests added in BS-003-R7 exist because of that.

BS-003-R7 removes `_unresolved` and makes `_closing` the single record every
consumer reads. Criterion 2's other claims - one close operation per model, peak
concurrent closes of 1, bounds on waiting rather than termination - were checked
again in R7 and still hold.

Criteria 1 and 3 above, and the earlier dated corrections in this file, are
unaffected.
