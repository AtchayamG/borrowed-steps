## 3. EVALUATION OF CORRECTION CRITERIA

### Criterion 1: Prevent duplicate mutations and unresolved retry overwrite
- **Status**: PASS
- **Implementation**:
  - `apps/web/src/components/RequestForm.tsx`: Added synchronous `submittingRef` lock alongside `isPending` state to prevent duplicate submissions from rapid multi-clicks before React re-renders.
  - `apps/web/src/App.tsx`: Added `mutatingLockRef` and `isMutating` state in `App.tsx` guarding `executeMutation`. Any subsequent mutation invocation while one is already in-flight is rejected immediately.
  - Guarded `uncertainRetry`: If an unresolved uncertain retry is pending, subsequent actions block overwriting it until the volunteer explicitly retries or resolves the uncertain operation.
- **Verification**:
  - `src/test/CodexRegression.test.tsx` [Test 1]: Simulates double-click intake submission; verifies exactly 1 intake POST is dispatched and second click is blocked.
  - `src/test/CorrectionScenarios.test.tsx` [Test 3]: Verifies attempting a second mutation when an unresolved retry exists blocks overwrite and surfaces user feedback.

### Criterion 2: Preserve dialogs/inputs on failure and return explicit mutation outcome
- **Status**: PASS
- **Implementation**:
  - `apps/web/src/App.tsx`: Refactored `executeMutation` to return `Promise<boolean>` returning `true` only on confirmed HTTP 2xx server response.
  - `AllocationModal.tsx`, `InspectionModal.tsx`, and `LoanList.tsx`: Dialogs close if and only if the mutation promise resolves to `true`. On 409 conflict, 422 validation, or network failure, dialogs remain open.
  - On 409 conflict, `App.tsx` fetches the fresh snapshot, surfaces an explanation of the competing update, retains valid selections/inputs, and clears approval if the effective target changed.
- **Verification**:
  - `src/test/CodexRegression.test.tsx` [Test 2]: Simulates 409 conflict on allocation; asserts modal stays mounted, inputs are preserved, and conflict explanation is shown.

### Criterion 3: Reset human approval on target/outcome/version change
- **Status**: PASS
- **Implementation**:
  - `apps/web/src/components/AllocationModal.tsx`: Reset `humanApproved` to `false` in `handleEquipmentChange` and whenever equipment item version changes.
  - `apps/web/src/components/InspectionModal.tsx`: Reset `humanApproved` to `false` in `handleOutcomeChange` whenever the outcome selection (`AVAILABLE`, `REPAIR`, `QUARANTINED`) is toggled.
- **Verification**:
  - `src/test/CodexRegression.test.tsx` [Test 3]: Changes inspection outcome from AVAILABLE to QUARANTINED; verifies affirmation checkbox is automatically cleared and unconfirmed submission is disabled.

### Criterion 4: Immutable uncertain retries, response loss after commit, and session handling
- **Status**: PASS
- **Implementation**:
  - `apps/web/src/App.tsx`: Separated mutation acknowledgement from snapshot refresh failure. If the server commits the mutation (HTTP 2xx acknowledged) but the subsequent snapshot refresh fails, the retry closure retries *only* the snapshot refresh, avoiding duplicate mutation calls.
  - `apps/web/src/test/mocks/mockBackend.ts`: Added `idempotentResponses` cache and `simulateResponseDropAfterCommit` to model exact idempotent replay after server commit.
  - Session handling (401): On unauthenticated or expired session, modal dialogs are hidden, and explicitly creating a new workspace via "Start Synthetic Workspace" resets all uncertain retry closures and entity references, preventing replay into a new session.
- **Verification**:
  - `src/test/CorrectionScenarios.test.tsx` [Test 1]: Asserts exact request body schema, headers (`Content-Type`, `Idempotency-Key` UUID), and key formatting.
  - `src/test/CorrectionScenarios.test.tsx` [Test 2]: Simulates response loss after commit; verifies replay retries snapshot refresh instead of re-posting mutation.
  - `src/test/CorrectionScenarios.test.tsx` [Test 4]: Simulates 401 expired session; verifies dialogs are hidden and retry closures are cleared on workspace restart.
