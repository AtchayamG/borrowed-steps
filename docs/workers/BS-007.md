## IMPLEMENTED

**Domain** (`domain/models.py`): `TaskKind` (PICKUP_DUE, RETURN_DUE),
`TaskStatus` (PENDING, DUE, RESOLVED), the `CoordinationTask` entity, two new
`EventAction` values, and two lookup helpers - `required_loan_status(kind)` and
`due_action(kind)` - so the loan state each notice applies to is stated once.
Standard library only.

**Ports** (`application/ports.py`): `Snapshot.tasks`; task reads and writes on
`WorkspaceUnitOfWork` (`list_tasks`, `get_task`, `find_task`,
`open_tasks_for_loan`, `add_task`, `resolve_task`, `mark_task_due`); and
`Store.due_task_candidates(now, limit)` returning `DueTaskRef` - two
identifiers, nothing else.

**Lifecycle** (`application/use_cases.py`): reservation opens a PENDING
`PICKUP_DUE` with `due_at = created_at =` the transaction clock; pickup resolves
it and opens a PENDING `RETURN_DUE` at `loan.due_at`; return resolves that;
inspection that closes a loan defensively resolves anything still open. All of
it runs inside the caller's existing transaction, beside the existing event and
idempotency writes.

**Processing** (`application/coordination.py`): `process_due_tasks` takes at
most `limit` candidates, then for each one reopens that task's own workspace
transaction and re-reads the task and its loan there. It transitions
PENDING -> DUE with a conditional update and writes the due event in the same
transaction, only when the update really moved a row. A task whose loan has
moved on resolves with no event. Returns a `TickReport` of counts.

**Storage** (`infrastructure/sqlite_store.py`): `_SCHEMA_V2` - the `tasks`
table with enum CHECKs, `UNIQUE(loan_id, kind)`, a composite foreign key on
`(workspace_id, loan_id)` (backed by a new unique index on
`loans(workspace_id, id)`), indexes on `(status, due_at, id)` and
`(workspace_id, created_at, id)`, and a one-time backfill of open loans only.
`_SCHEMA_V1` is untouched.

**Runner** (`infrastructure/task_runner.py`): one `threading.Thread`, an
immediate startup tick, then an interruptible 30-second wait. `stop(timeout)`
joins with a bound and returns whether the thread really ended.

**Wiring** (`interfaces/http/app.py`, `config.py`): `BS_TASKS_ENABLED` default
true; `tasks` on both snapshot-carrying responses; `MILESTONE = "M2B"`; the
runner started and stopped by the lifespan, its stop awaited through
`asyncio.to_thread` so the event loop is never blocked, with the inference drain
in a `finally` so it cannot be skipped.

## Two deliberate design decisions worth review

1. **`StorageBusyError` (`application/errors.py`).** The tick has to recognise
   contention, but the application layer must not import a database driver. The
   SQLite adapter now translates a lock failure on `BEGIN` into this port-level
   exception. It is intentionally **not** a `CodedError`: adding one would change
   the frozen error contract. HTTP behaviour is unchanged - it reaches the same
   generic handler the raw `sqlite3.OperationalError` did.
2. **Discovery returns identifiers only.** `due_task_candidates` is the one
   cross-workspace capability. It reads two ids per row, no route calls it, and
   nothing it returns reaches a response or a model. Every decision is re-made
   inside the candidate's own workspace transaction.

## KNOWN_ISSUES

- **A pre-existing flake in the baseline, not caused by this task and not
  fixed.** On the very first baseline run at `8189db0`, before any edit,
  `test_smoke_prerequisite.py::test_healthy_snapshots_still_let_a_passing_case_run`
  failed; every later run of the same commit passed. Cause identified:
  `scripts/assistant_smoke._cases()` builds its dates from
  `datetime.now(UTC)` while keeping the current hour and minute
  (`assistant_smoke.py:164`, `:170`), and the test calls `_cases()` once to
  build the fake response while the code under test calls it again. A minute
  rollover between those two calls changes the expected `due_at` and the case
  fails. I did **not** change it: the dispatch forbids modifying historical live
  proof scripts. Flagged for Codex as a one-line fix (compute the cases once)
  whenever that file is next in scope.
- **Ordering ties are decided by the opaque id.** The contract's order is
  `created_at` then `id`. When a pickup and a return notice are created within
  the same second - which happens under a test clock that does not advance, and
  could happen in production - `created_at` ties and the random id decides. This
  is the contract's own rule, and it is now asserted explicitly rather than
  assumed to match insertion order. Two of my own tests initially assumed
  insertion order and were wrong; they were corrected, not the code.
- `SqliteStore.__init__` runs the migration check inside a write transaction, so
  constructing a store while another writer holds the lock raises rather than
  waiting past the busy timeout. Pre-existing behaviour from v1, unchanged here;
  it only affects process start, not ticks.
- Backfilled task ids come from SQLite's `randomblob(12)` rather than the
  application's CSPRNG generator, because the migration runs before any
  generator exists. They match the same 24-hex-character shape, and task ids are
  opaque handles inside a workspace-scoped read, not a security boundary.
- Nothing here has been exercised in a browser, and no frontend work is included.
