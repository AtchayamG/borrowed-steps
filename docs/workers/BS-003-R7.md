## The defect, stated exactly

BS-003-R6 left the interpreter with **two** records of outstanding cleanup:

- `_closing: dict[model, Task]`, entered when a close operation starts, and
- `_unresolved: list[model]`, appended in `_close`'s failure tail.

Everything that had to make a decision read `_unresolved`: the refusal at the
top of `interpret`, the `cleanup_unresolved` property the HTTP slot consults,
and the loop in `resolve_cleanup` that shutdown drains.

A cancellation arriving while a close was still running raised out of
`_await_close` and left `_close` immediately - so it never reached the failure
tail, and `_unresolved` stayed empty. At that moment `_closing` held a live
close task for a model whose `client_open` was still `True`, and every consumer
reported nothing outstanding. The slot looked free. The next request was served
and opened a second client on the same interpreter.

Two records that can disagree is the whole bug. One record cannot.

## IMPLEMENTED

**One record.** `_unresolved` is gone, from `__slots__` and from the code.
`_closing` is now the only account of outstanding cleanup. A model enters it in
`_close_operation`, at the moment its close begins and before anything awaits
it, so no exit path - a cancelled waiter least of all - can leave an open client
unaccounted for.

**Leaving the record requires evidence.** `_reconcile_closes` deletes an entry
only when its task is `done()` *and* `model.client_open` is False. A close whose
waiter was cancelled stays recorded on purpose, and is released later by
observation rather than by assumption. `cleanup_unresolved` reconciles first and
then reports, so a close that completed after its waiter gave up stops counting
as outstanding without anyone having to poll for it.

**Every consumer reads that one record.** `cleanup_unresolved` returns
`bool(self._closing)`. `resolve_cleanup` reconciles, iterates `self._closing`,
deletes only confirmed-closed models, and returns `not self._closing`. The
refusal at the top of `interpret` now reads the `cleanup_unresolved` property
rather than a field, which is what makes it see a close whose waiter was
cancelled.

**The terminal diagnostic survives the cancellation.** `_close` catches
`asyncio.CancelledError`, sets `telemetry.cleanup = "close_cancelled"`, logs
that the close is still running and still owned, and re-raises. `interpret`'s
`finally` catches it in turn, marks the outcome `interrupted` with reason
`cancelled_during_cleanup` when the run had not already failed for another
reason, emits the record, and re-raises the original cancellation. Between
emitting and re-raising there is no `await`, so a second cancellation cannot
land in the gap and cost the run its only account of what it charged and what it
left open.

Cancellation is still a request. Nothing here claims a resistant close can be
forced to stop; the bound remains on waiting. What changed is that a close
nobody is waiting for any more is still visible.

## KNOWN_ISSUES

- A close that swallows cancellation still cannot be stopped from this process.
  It is now reliably owned, observed and reported unresolved on every path,
  including a cancelled waiter. It is not terminated. The bound is on waiting.
- `_reconcile_closes` runs from `cleanup_unresolved`, which the HTTP slot reads
  on the application's event loop and the tests poll from the pytest thread. It
  is a plain dict read plus a delete with no `await` inside, so it cannot be
  interleaved on the loop; a genuinely concurrent reader in another thread is
  relying on CPython's dict semantics rather than on a lock. No production
  caller does that today - worth a reviewer's eye if one ever will.
- An abandoned close is released only when someone asks. Nothing polls, so an
  idle service with a finished close keeps the entry until the next request,
  health read or shutdown. That is conservative in the safe direction.
- The shutdown drain has still not been exercised against a real stalled model.
- Extraction accuracy - the BS-003-R3 `equipment_kind` omission - is untouched
  here and unresolved. No prompt, schema description or provider changed.
