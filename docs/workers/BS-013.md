## Implemented and Verified

Wired the accepted `PostgresStore` into an explicit hosted FastAPI runtime (`create_app`) and proved the existing structured human-in-the-loop workflow over HTTP against real disposable PostgreSQL 16.10 databases. Assistant inference and autonomous task scheduling remain explicitly disabled in this increment.

All required verification and frozen task decisions were satisfied:

1. **Configuration Matrix & Invariants**:
   - `runtime` values: `"local"` | `"hosted"`. `store` values: `"sqlite"` | `"postgres"`.
   - Local defaults to SQLite; hosted requires explicitly selected PostgreSQL. Invalid combinations fail closed immediately.
   - Hosted mode strictly requires private `BS_DATABASE_URL`, `BS_COOKIE_SECURE=1`, `BS_TASKS_ENABLED=0`, `BS_ASSISTANT_ENABLED=0`, `BS_ASSISTANT_PROVIDER=groq`, and a non-empty HTTPS allowlist in `BS_ALLOWED_ORIGINS`.
   - Hosted origin allowlist rejects wildcards, credentials, paths, queries, fragments, invalid ports, and loopback/localhost addresses.
   - Database URLs and credentials are excluded from `repr`, string formatting, and error messages (`repr=False`).
   - Direct `Settings` construction cannot bypass hosted validation (`Settings.__post_init__` and `validate_settings` enforce the matrix).

2. **Factory Initialization & Schema Gate**:
   - `create_app` validates settings at startup.
   - `PostgresStore` is imported lazily only when `runtime == "hosted"`, preserving clean local installation without mandatory PostgreSQL dependencies.
   - `store.check_schema()` is called read-only at startup before serving any requests. Startup fails closed with `SchemaVersionError` if schema is version 0 (unmigrated) or version > 1 (future schema). No tables or migrations are created at runtime.
   - `TaskRunner` is not instantiated (`app.state.tasks = None`).
   - Assistant is disabled (`assistant = None`). Injected interpreters in test harnesses cannot bypass the hosted disabled gate.
   - `/api/health` returns `status: "ok"`, `milestone: "M3"`, and `agent_mode: "disabled"` without running database queries or migrations.

3. **Real PostgreSQL HTTP Integration**:
   - Tests execute against disposable PostgreSQL 16.10 databases on loopback (`127.0.0.1:54339`) using synthetic origin `https://borrowed-steps.example`.
   - Proved workspace creation with `Secure`, `HttpOnly`, `SameSite=lax` session cookie.
   - Verified structured human workflow: `POST /api/requests`, human approval refusal (`422 APPROVAL_REQUIRED`), valid reservation, loan pickup (`ON_LOAN`), loan return (`AWAITING_INSPECTION`), item inspection (`QUARANTINED`/`AVAILABLE`), and persisted snapshot verification (`GET /api/snapshot`).
   - Missing or unlisted Origin headers return `403 ORIGIN_FORBIDDEN`.
   - Assistant intake endpoint (`POST /api/intake/interpret`) returns `503 ASSISTANT_DISABLED` without mutating state.

4. **Session Isolation & Foreign ID Protection**:
   - Requests without session cookies return `401 SESSION_REQUIRED`.
   - Attempting to mutate a workspace using entity IDs from another workspace fails with `404 NOT_FOUND`.

5. **Persistence & Exact Idempotency Replay**:
   - Verified across separate `create_app` instances connected to the same PostgreSQL database.
   - Identical idempotency key and payload return exact byte-identical replay from stored text.
   - Mismatched payload with previously used key returns `409 IDEMPOTENCY_CONFLICT`.

6. **Deterministic HTTP Concurrency Proofs**:
   - Competing allocators: Two concurrent HTTP clients attempting to allocate the same equipment item via barrier synchronization. Exactly one succeeds with `200` and the other receives `409 STATE_CONFLICT`. Directly verified exactly one loan was created in PostgreSQL.
   - Identical idempotency envelopes: Two concurrent HTTP clients submitting identical mutation requests with the same key via barrier synchronization. Both receive `200` with byte-identical responses, producing exactly one request record in PostgreSQL.
